## 0. 우리가 푸는 문제 (도메인)
본로이는 의료소모품 **유통사**다. 흐름은:
1. **병원(지점)이 주문**을 준다 (텍스트·이미지·엑셀 등 제각각).
2. 우리가 그걸 정리해 **여러 거래처에 나눠 발주**한다 (거래처마다 가격·배송비·재고가 다름).
3. 거래처가 **실제 출고 수량·단가·배송비**를 거래명세서로 알려준다.
4. 그걸 **최종 "종합 주문 내역"(매입 장부)에 쌓는다** → 마진·정산·세금계산서의 기준.

## 2. 핵심 데이터 흐름과 "왜 이렇게 됐나"
- **두 갈래가 겹쳐 있다**: ① 주문 관리(`orders`)와 ② 확보 관리(소싱, `sourcing_*`)가 둘 다 "병원 주문 → 거래처별 발주"를 한다. 소싱이 **나중에 추가된 똑똑한 버전**(AI 파싱·가격비교·출고확인서 반영)이고, 옛 발주 관리(`purchase_orders`)는 사실상 안 쓴다(0건).
- **끊겼던 마지막 고리를 이번에 연결**: 소싱은 끝나도 어디에도 안 쌓였다. 이제 **거래처 "완료"(또는 출고확인서 반영) → `orders`/`order_items` 한 건 생성 → 주문 내역에 누적**된다. 멱등성은 `sourcing_settlements.order_id`로 보장(완료 취소/재반영 시 그 주문만 교체).
- **무로그인(anon) 운영**: 빠른 사용을 위해 로그인 게이트를 끄고 anon 키로 쓴다. 그 대가로 모든 테이블이 공개 상태(보안 부채).

## 3. PO가 정한 방향 (결정 완료 — 미결 아님)
1. **로그인 도입**: 지금은 **보류**. 시스템이 안정화되면 도입한다 → §5 다음 과제로 기록. (`NEXT_PUBLIC_AUTH_ENABLED`로 켤 수 있게 이미 준비됨)
2. **안 쓰는 화면(발주 관리·반품 관리·문서 생성·분석/리포트)**: **삭제하지 않는다. 메뉴(사이드바)에서만 숨기고 코드는 보존**한다. 나중에 부활 가능하게.
3. **주문 관리 ↔ 소싱 일원화**: **소싱으로 통합**하는 방향. 단 **큰 변경**이므로 — 기존 주문 220건 **보존**, 합치는 계획을 **먼저 쉬운 말로 보여주고 PO 승인받은 뒤** 진행. **한 번에 갈아엎지 않는다(점진적).**
4. **`/api/invoice` 로그인 의존 제거**: 무로그인 환경에서도 엑셀 거래명세서가 되도록 **로그인 요구를 푼다.**
